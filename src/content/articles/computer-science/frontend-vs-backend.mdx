<Key title="Short answer">

**Frontend vs backend** divides a web application into two sides. The frontend is the part that runs in the user's browser, built with HTML, CSS and JavaScript, and handles layout and interaction. The backend runs on servers, holds the business logic, talks to databases and returns data to the frontend over HTTP, usually as JSON.

</Key>

Frontend vs backend is the first split most people meet when they learn web development. Click "Pay" on a shopping site and the button, the form and the spinner belong to the frontend; checking stock, charging the card and saving the order happen on the backend. The two are separate programs, often written in different languages, joined by HTTP requests.

## What frontend development covers

The frontend (client side) is everything the browser downloads and runs. Browsers natively understand three languages:

- HTML for structure and content (headings, forms, buttons), defined by the WHATWG HTML Living Standard.
- CSS for layout, colour, fonts and responsive design for different screen sizes.
- JavaScript (standardised as ECMAScript, ECMA-262) for behaviour: reacting to clicks, validating input as the user types, fetching data and updating the page without a reload. Browsers also run WebAssembly.

Most teams use a framework such as React, Angular or Vue to build the interface from reusable components, plus build tools that bundle and minify the code. Frontend developers also handle accessibility to the W3C WCAG guidelines, cross-browser testing and the perceived speed of the page.

## What backend development covers

The backend (server side) runs on machines the user never sees. It handles:

- receiving requests from the frontend and other clients, usually through an API;
- applying business rules, such as prices, permissions and stock checks;
- reading and writing data in databases, relational or NoSQL (see [SQL vs NoSQL](/computer-science/sql-vs-nosql/));
- authentication, sessions and access control;
- talking to other services, such as payment gateways, email and file storage.

Backends are written in many languages: JavaScript on Node.js, Python, Java, C#, Go, PHP and Ruby, each with web frameworks. Some are compiled and some interpreted, a difference explained in [compiled vs interpreted languages](/computer-science/compiled-vs-interpreted-languages/). Backend work also includes deployment, logging, scaling and keeping the service available.

The two sides communicate through HTTP, as described in [how HTTP works](/computer-science/how-http-works/). The frontend sends a request with a method (GET, POST, PUT, DELETE), a path such as /api/orders, headers and sometimes a body. The backend replies with a status code such as 200 OK, 404 Not Found or 500 Internal Server Error, plus a body that is usually JSON.

The contract between the two is the API. Many APIs follow the REST style described by Roy Fielding, where URLs name resources and HTTP methods act on them; see [REST API basics](/computer-science/rest-api-basics/). When the frontend and backend sit on different origins, the browser enforces the CORS rules of the Fetch Standard, so the backend must send headers that allow the frontend's origin.

Pages can be built in different places. With server-side rendering, the backend sends finished HTML. With client-side rendering, the backend sends JSON and JavaScript in the browser builds the page. Many modern sites mix the two.

## Frontend vs backend comparison

| Aspect | Frontend | Backend |
| --- | --- | --- |
| Runs on | User's browser or device | Servers or cloud |
| Main concern | Layout, interaction, accessibility | Business logic, data, security |
| Core languages | HTML, CSS, JavaScript | JavaScript (Node.js), Python, Java, C#, Go, PHP, Ruby |
| Typical frameworks | React, Angular, Vue | Express, Django, Spring, ASP.NET |
| Data storage | Browser storage, cache | Relational and NoSQL databases |
| Visible to user | Yes, code can be inspected | No, code stays on the server |
| Testing | UI, browser and accessibility tests | Unit, integration and load tests |
| Typical bugs | Layout breaks, slow rendering | Wrong data, slow queries, outages |

Both sides need the testing levels covered in [types of software testing](/computer-science/types-of-software-testing/).

## Security on both sides

Never trust the client. Anyone can open the browser's developer tools and change frontend code or send their own requests, so frontend validation only improves the user's experience. The backend must validate every input again, check permissions on every request and store passwords hashed.

The OWASP Top 10:2021 lists the most serious web risks. Broken access control is number one and is a backend responsibility. Injection, which in the 2021 list includes cross-site scripting, needs care on both sides: parameterised queries on the backend and safe output encoding on the frontend. All traffic between the two should use HTTPS.

## Performance: where the time goes

Each request from the browser costs a network round trip time (RTT) plus the time the server spends on it. If the frontend makes n requests one after another, the waiting time is roughly:

$$
T = n \times (RTT + t_s)
$$

where t_s is the server processing time per request. When the backend gathers the same data in one request, the frontend pays only one round trip:

$$
T = RTT + n \times t_s
$$

<dt>Solution</dt><dd>Three requests: T = 3 × (80 + 20) = 300 ms<br />One combined request: T = 80 + 3 × 20 = 140 ms<br />Saving = 300 − 140 = 160 ms</dd>
<dt>Answer</dt><dd><strong>About 300 ms with three sequential requests and about 140 ms with one combined endpoint</strong></dd>
<dt>Limitations</dt><dd>Real pages often send requests in parallel, and HTTP/2 multiplexing and caching change the numbers; measure with the browser's network tools.</dd>

## Key formulas for frontend vs backend performance

| Quantity | Formula | Symbols and units |
| --- | --- | --- |
| Sequential requests | T = n × (RTT + t_s) | T total wait in ms, n number of requests, RTT round trip time in ms, t_s server time per request in ms |
| One combined request | T = RTT + n × t_s | Same symbols; the backend does the n pieces of work in one request |

## Full stack and choosing a path

A full stack developer covers both sides. In small teams that is common; in larger teams frontend and backend specialists agree on an API and work in parallel. If you enjoy visual design, user interaction and fast feedback, start with the frontend. If you prefer data, algorithms and system design, the backend suits you better. Backend work leans on data structures and databases, for example [database normalization](/computer-science/database-normalization/).

## Frontend vs backend interview and viva questions

1. **What is the main difference between frontend and backend?** The frontend runs in the user's browser and handles what the user sees and does; the backend runs on servers and handles business logic, data storage and security.
2. **Which languages run natively in a web browser?** HTML, CSS and JavaScript, along with WebAssembly.
3. **Why must the backend validate input even when the frontend already does?** Users can change frontend code or send their own requests, so the server cannot trust anything that comes from the client.
4. **What is CORS?** A browser rule from the Fetch Standard that blocks a page from reading responses from another origin unless that server sends headers allowing it.
5. **What is the difference between server-side and client-side rendering?** In server-side rendering the backend sends finished HTML; in client-side rendering it sends data, and JavaScript in the browser builds the page.
