<Key title="Short answer">

The main **types of software testing** by level are **unit testing** of single functions or classes, **integration testing** of components working together, **system testing** of the complete application against its requirements and **acceptance testing** by users. Tests are also grouped as functional or non-functional, and as black box or white box.

</Key>

Software testing checks that a program behaves as intended and finds defects before users do. No single kind of test can catch every problem, so teams combine several types at different levels. Knowing what each type covers, and how much of each to write, is the basis of an effective test strategy.

## Types of software testing by level

### Unit testing

A unit test exercises the smallest testable part of the code, usually a function, method or class, in isolation. Dependencies such as databases, networks or clocks are replaced with **test doubles** (mocks, stubs or fakes). Unit tests are written by developers, run in milliseconds and pinpoint failures precisely. Designing code with clear dependencies, as the [SOLID principles](/computer-science/solid-principles/) recommend, makes unit testing much easier.

```python
def discount(price, percent):
    if not 0 <= percent <= 100:
        raise ValueError("percent must be 0 to 100")
    return round(price * (100 - percent) / 100, 2)

def test_discount_normal():
    assert discount(200.0, 10) == 180.0

def test_discount_boundaries():
    assert discount(50.0, 0) == 50.0
    assert discount(50.0, 100) == 0.0
```

### Integration testing

Integration tests check that units work together: the application with its real database, two services calling each other, or code calling an external payment API. They catch problems unit tests cannot, such as wrong SQL, mismatched data formats, configuration errors and incorrect assumptions about another component. Testing a [REST API](/computer-science/rest-api-basics/) endpoint against a test database is a typical example.

### System testing

System tests check the fully integrated application in an environment close to production, against its specified requirements. They are usually black box: testers drive the system through its user interface or public API without looking at the code. End-to-end (E2E) tests that simulate a user journey through the browser, such as "search, add to cart, pay", belong here.

### Acceptance testing

Acceptance testing decides whether the software is ready to be accepted by its users or customer. **User acceptance testing (UAT)** has real users try business scenarios; **alpha and beta testing** expose the product to internal and then external users; **contractual or regulatory acceptance** checks formal criteria.

Mike Cohn's test pyramid suggests a large number of fast unit tests at the base, fewer integration tests in the middle and a small number of slow, brittle end-to-end tests at the top. This keeps feedback fast and failures easy to diagnose while still checking the whole system. An "ice cream cone", with mostly manual and E2E tests, is slow and costly to maintain.

## Functional and non-functional testing

**Functional testing** checks what the system does against requirements: correct outputs, business rules, error handling. Techniques include **equivalence partitioning** (one test per class of similar inputs) and **boundary value analysis** (tests at and around limits, where bugs cluster).

**Non-functional testing** checks how well it does it:

- **Performance testing:** response time and throughput under expected load; **load** and **stress** testing push beyond normal levels; **soak** testing runs for long periods to reveal leaks.
- **Security testing:** vulnerability scanning, penetration testing, checks for injection and authentication flaws.
- **Usability and accessibility testing:** whether people, including those using assistive technologies, can use it effectively.
- **Compatibility testing:** different browsers, devices and operating systems.
- **Reliability and recovery testing:** behaviour when components fail.

## Black box, white box and grey box

- **Black box:** tests are based on requirements and behaviour, without knowledge of the code.
- **White box:** tests are designed from the code structure, aiming at statement, branch or path coverage.
- **Grey box:** testers know some internals, such as the database schema, but test through external interfaces.

## Other common test types

- **Smoke testing:** a quick check that the main functions work after a build or deployment.
- **Sanity testing:** a narrow check that a specific fix works.
- **Regression testing:** re-running tests after changes to catch side effects.
- **Exploratory testing:** skilled testers investigate the software freely, learning and designing tests as they go.
- **Static testing:** reviews and static analysis of code and documents without running them.

## Manual and automated testing

**Manual testing** is done by people following test cases or exploring freely. It suits usability checks, exploratory testing and features that change too often to automate. **Automated testing** uses scripts and frameworks such as pytest, JUnit, Jest, Selenium or Playwright to run tests repeatedly at no extra cost per run. Automation pays off for regression tests, which run on every change, and for tests that need precise timing or large data volumes. Most teams automate the bulk of unit, integration and regression tests and keep manual effort for exploratory and acceptance work.

## Test cases and documentation

A test case records the preconditions, input data, steps and expected result, and links to the requirement it checks. Test plans describe scope, approach, environments, schedule and exit criteria for a release. Defect reports describe how to reproduce a failure, the expected and actual results, severity and priority. Standards such as ISO/IEC/IEEE 29119 and the ISTQB syllabus give common terms and templates, which help teams and clients communicate clearly about quality.

## Measuring test effectiveness

Code coverage tools report which lines and branches the tests execute. High coverage does not guarantee good tests, but low coverage shows clearly which code is never checked. Mutation testing goes further by deliberately introducing small faults into the code and checking that at least one test fails for each; surviving mutants reveal weak assertions. Defect trends, escaped defects found in production and the time taken to run the suite are other useful measures of how well a testing process works.

## Building a testing strategy

1. Write unit tests alongside the code; consider test-driven development for complex logic.
2. Add integration tests for every boundary: database, message queue, external API.
3. Keep a small, stable set of end-to-end tests for critical user journeys.
4. Run all automated tests in continuous integration on every change.
5. Add performance and security testing before major releases and for high risk features.
6. Track defects found in production and add tests that would have caught them.

Testing applies to every layer covered in this series, from database schemas designed by [normalization](/computer-science/database-normalization/) to the [HTTP](/computer-science/how-http-works/) behaviour of web applications and the efficiency of algorithms measured with [Big O notation](/computer-science/big-o-notation/).

## Types of software testing interview and viva questions

1. **What is the difference between a unit test and an integration test?** A unit test checks one function, method or class in isolation with its dependencies replaced by test doubles. An integration test checks that real components, such as the application and its database, work together.
2. **What does the test pyramid recommend?** Many fast unit tests at the base, fewer integration tests in the middle and a small number of slow end-to-end tests at the top, which keeps feedback fast and failures easy to diagnose.
3. **What is boundary value analysis?** It designs tests at and around the limits of valid input ranges, because defects tend to cluster at boundaries.
4. **How does black box testing differ from white box testing?** Black box tests are based on requirements and behaviour without knowledge of the code, while white box tests are designed from the code structure to reach statement, branch or path coverage.
5. **Why does high code coverage not guarantee good tests?** Coverage only shows which lines and branches ran, not whether the assertions would catch a fault; mutation testing reveals weak assertions by checking that injected faults make a test fail.
