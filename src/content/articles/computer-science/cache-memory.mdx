  - q: "Why is cache memory faster than main memory?"
    a: "Caches are built from SRAM placed on the processor chip, close to the core, while main memory is DRAM on separate chips reached over a memory bus. SRAM needs no refresh and is faster per access, but it uses more transistors per bit, so it is more expensive and caches are kept small."

<Key title="Short answer">

**Cache memory** is a small, fast SRAM store between the processor and main memory that keeps copies of recently used blocks. Processors use several levels, L1, L2 and L3, each larger and slower. A mapping scheme (direct, fully associative or set associative) decides where a memory block may be placed in the cache.

</Key>

Cache memory exists because a processor core can execute instructions far faster than DRAM main memory can deliver them. Without a cache the core would wait on almost every load. A cache keeps copies of the data and instructions the program is likely to need next, so most accesses finish in a few cycles instead of making the long trip to main memory.

## Why cache memory works: locality

Caches rely on the **principle of locality**, which Hennessy and Patterson describe as one of the most important program properties. It comes in two forms. With temporal locality, an item used now is likely to be used again soon, such as a loop counter or the instructions of a loop body. With spatial locality, items whose addresses are near each other tend to be used close together in time, such as consecutive elements of an array.

A cache does not fetch single bytes. It moves fixed size **blocks** (also called **lines**), so a miss on one element brings its neighbours in too. That is one reason contiguous data structures run faster, as shown in [arrays vs linked lists](/computer-science/arrays-vs-linked-lists/).

Modern processors use a hierarchy of caches, each level larger and slower than the one above it.

The L1 cache is the smallest and fastest. It sits inside each core and is usually split into an instruction cache and a data cache, so the core can fetch an instruction and load data in the same cycle. This split is the modified Harvard idea explained in [Von Neumann vs Harvard architecture](/computer-science/von-neumann-vs-harvard-architecture/). The L2 cache is larger and slower, usually unified (instructions and data together) and private to each core. The L3 cache is the largest on chip cache, usually shared by all cores, and the last stop before main memory.

For a real example, Hennessy and Patterson describe the Intel Core i7 6700 with a 32 KB, 8 way L1 instruction cache and a 32 KB, 8 way L1 data cache per core, a 256 KB, 4 way L2 cache per core, and an 8 MB, 16 way L3 cache shared by the cores, all using 64 byte blocks.

When the core issues a load, the L1 cache is checked first. On a **hit** the data comes back in the hit time. On a **miss** the request goes to L2, then L3, then main memory, and the block that contains the address is copied back up into the caches.

## Cache memory mapping techniques

A cache holds far fewer blocks than main memory, so it needs a rule for where each memory block may go.

### Direct mapping

Each memory block can go into exactly one cache line:

$$
\text{line} = (\text{block address}) \bmod (\text{number of lines})
$$

The hardware is simple and fast because only one tag is compared. The weakness is **conflict misses**: two frequently used blocks that map to the same line keep evicting each other, even when the rest of the cache is empty.

### Fully associative mapping

A block can go into any line. The cache must compare the address tag with the tag of every line in parallel, which needs one comparator per line. It has no conflict misses but costs the most hardware and power, so it is used only for small structures such as translation lookaside buffers.

### Set associative mapping

The cache is divided into **sets** of n lines each (n way set associative). A block maps to exactly one set, then may go in any line within that set:

$$
\text{set} = (\text{block address}) \bmod (\text{number of sets})
$$

Only n tags are compared per access. Direct mapping is the 1 way case and fully associative is the case of one set holding every line. Most processor caches are 2 way to 16 way set associative, as the i7 example shows.

## How the address is split

For lookup, the cache divides the physical address into three fields:

| Field | Bits | Purpose |
| --- | --- | --- |
| Tag | remaining high bits | Stored with the line and compared to confirm a hit |
| Index | log2(number of sets) | Selects the set (or the line in a direct mapped cache) |
| Block offset | log2(block size in bytes) | Selects the byte within the block |

Each line also holds a **valid bit**, and a write back cache adds a **dirty bit**. A hit requires the valid bit to be set and the stored tag to match.

For comparison, the same cache direct mapped would have 512 sets, so 9 index bits and a 17 bit tag; fully associative would have no index and a 26 bit tag.

## Write policies

A **write through** cache updates both the cache and the next level on every write. It is simple and keeps memory up to date, but it creates heavy write traffic, so a write buffer is normally added.

A **write back** cache updates only the cache line and sets its dirty bit. The block goes to the next level only when it is evicted. That saves bandwidth, and it is the common choice for L2 and L3.

On a write miss, **write allocate** fetches the block into the cache and then writes it, while **no write allocate** writes straight to the next level. Write back caches usually use write allocate.

## Replacement policies

In a set associative or fully associative cache, a miss in a full set must evict one line. Least recently used (LRU) evicts the line unused for the longest time, which suits temporal locality, but true LRU becomes costly at high associativity, so hardware often uses an approximation. First in, first out (FIFO) evicts the oldest line. Random replacement is simple to build and, for large caches, comes close to LRU in miss rate.

A direct mapped cache needs no policy because each block has only one possible line.

## Types of cache misses

Hennessy and Patterson group misses into the **three Cs**:

1. Compulsory misses happen on the first access to a block, which cannot be in the cache yet. Larger blocks reduce them.
2. Capacity misses happen because the cache cannot hold every block the program needs. A larger cache reduces them.
3. Conflict misses happen when too many blocks map to the same set. Higher associativity reduces them.

With several cores there is a fourth kind, **coherence misses**, which come from keeping private caches consistent with each other.

## Key formulas for cache memory

| Quantity | Formula | Symbols and units |
| --- | --- | --- |
| Number of lines | lines = cache size ÷ block size | bytes ÷ bytes |
| Number of sets | sets = lines ÷ n | n = associativity (ways) |
| Offset bits | log2(block size) | bits |
| Index bits | log2(sets) | bits |
| Tag bits | address bits − index bits − offset bits | bits |
| AMAT | hit time + miss rate × miss penalty | cycles or ns |
| Two level AMAT | hit time L1 + miss rate L1 × (hit time L2 + miss rate L2 × miss penalty L2) | cycles; miss rate L2 is local |

$$
\text{AMAT} = t_\text{hit} + m \times t_\text{penalty}
$$

## Cache memory interview and viva questions

1. **What is cache memory?** A small, fast SRAM memory between the processor and main memory that holds copies of recently used blocks so most accesses avoid the slow DRAM.
2. **What is the difference between direct mapped and set associative caches?** In a direct mapped cache each block has one possible line; in an n way set associative cache it maps to one set and may use any of n lines there, which reduces conflict misses.
3. **How is a memory address divided for cache lookup?** Into a tag, an index that selects the set, and a block offset that selects the byte within the block.
4. **What is the difference between write through and write back?** Write through updates the next level on every write; write back updates only the cache and writes the dirty block out when it is evicted.
5. **What are the three Cs of cache misses?** Compulsory misses on first access, capacity misses when the working set is too large, and conflict misses when too many blocks map to one set.
