<Key title="Short answer">

In **compiled vs interpreted languages**, the difference is when source code is translated. A **compiler** translates the whole program into machine code before it runs, producing an executable (C, C++, Rust, Go). An **interpreter** reads and executes the program statement by statement at run time (classic BASIC, shell scripts). Many modern languages mix both: Java, C# and Python compile to **bytecode** that a virtual machine interprets or **JIT** compiles while the program runs.

</Key>

A processor only executes machine code: binary instructions for its own instruction set. Programs written in high level languages must be translated before the hardware can run them. Whether that translation happens once in advance or continuously while the program runs affects speed, portability, error checking and the development workflow. Strictly speaking, "compiled" and "interpreted" describe implementations, not languages, but most languages have a usual implementation, which is what people mean.

A compiler works in stages:

1. **Lexical analysis** splits the text into tokens: keywords, names, numbers and symbols.
2. **Parsing** checks the grammar and builds a syntax tree.
3. **Semantic analysis** checks types, scopes and declarations.
4. **Intermediate representation and optimisation** rewrite the program to run faster or use less memory, for example by removing dead code or inlining small functions.
5. **Code generation** emits machine code for a particular processor and operating system.
6. **Linking** combines the program with libraries into an executable.

Because all of this happens before the program runs, many errors are caught at build time and the resulting executable runs at full hardware speed. The cost is a build step after every change and a separate executable for each target platform.

## How an interpreter works

An interpreter also parses the source, but instead of producing an executable it carries out the operations directly. A simple interpreter walks the syntax tree and performs each statement as it reaches it. Most practical interpreters first translate source into a compact **bytecode** and then run a loop that fetches, decodes and executes one bytecode instruction at a time, much like a software processor.

Interpreters start immediately and make interactive work easy: type a line, see the result. The same program runs anywhere the interpreter exists. The cost is speed, since every instruction pays a translation overhead each time it runs, and errors such as a misspelt variable may appear only when that line executes.

## Bytecode, virtual machines and JIT

Many languages sit between the two extremes:

- **Java and Kotlin** compile to JVM bytecode; **C#** compiles to .NET intermediate language.
- A **virtual machine** loads that bytecode on any platform, interprets it at first and profiles which methods run most often.
- A **just-in-time (JIT) compiler** then compiles those hot methods to native machine code while the program runs, using information about the actual data to optimise aggressively.
- **JavaScript** engines in browsers use the same idea, starting with an interpreter and JIT compiling hot functions.

This gives portability ("compile once, run on any JVM") with speed close to compiled code after a short warm-up.

## Transpilers and WebAssembly

Some tools translate between high level languages rather than into machine code. TypeScript is compiled (transpiled) to JavaScript, and many languages can be compiled to **WebAssembly**, a compact binary format that browsers run at near native speed. This blurs the line further: a C++ library can be compiled once to WebAssembly and then run inside a browser alongside interpreted and JIT compiled JavaScript.

## Compile time and run time errors

A compiler for a statically typed language rejects many mistakes before the program runs: calling a function with the wrong number or type of arguments, using an undeclared variable, or returning the wrong type. In dynamically typed, interpreted languages the same mistakes appear only when the faulty line executes, possibly in production. Linters, type hints (for example in Python) and automated tests close much of this gap.

## Compiled vs interpreted languages: comparison

| Feature | Compiled (ahead of time) | Interpreted |
| --- | --- | --- |
| Translation | Once, before running | Every run, while running |
| Output | Native executable | No separate executable |
| Execution speed | Usually fastest | Slower, unless JIT compiled |
| Start-up | Instant once built | Instant, no build step |
| Error detection | Many errors at compile time | Many errors only at run time |
| Portability | Rebuild for each platform | Runs wherever the interpreter runs |
| Source distribution | Can ship binary only | Source or bytecode usually shipped |
| Typical languages | C, C++, Rust, Go, Fortran | Python, Ruby, PHP, shell, classic BASIC |

## Which should you choose?

- **Systems software, embedded firmware and games** need predictable speed and low memory, so compiled languages such as C, C++ and Rust dominate. Firmware for a [microcontroller](/electronics-engineering/microcontroller-vs-microprocessor/) is almost always compiled.
- **Scripting, data analysis and automation** value fast development, so Python and similar languages are common.
- **Enterprise and Android applications** often use JVM languages for portability and mature tooling.
- **Web front ends** use JavaScript or languages compiled to JavaScript or WebAssembly, served over the [HTTP request and response](/computer-science/how-http-works/) cycle.

Performance also depends far more on the algorithm than on the language: an O(n²) algorithm in C will lose to an O(n log n) algorithm in Python for large inputs, as [Big O notation](/computer-science/big-o-notation/) explains. How the processor fetches compiled instructions from memory is covered in [Von Neumann vs Harvard architecture](/computer-science/von-neumann-vs-harvard-architecture/).
