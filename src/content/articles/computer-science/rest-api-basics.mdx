<Key title="Short answer">

A **REST API** exposes an application's data as **resources** identified by URLs, such as /users/42. Clients use standard **HTTP methods**: GET to read, POST to create, PUT or PATCH to update and DELETE to remove. The server replies with a **status code** and usually JSON. Each request is **stateless**, so REST APIs scale and cache well.

</Key>

Mobile apps, web front ends, IoT devices and other services all talk to backends through APIs. REST (Representational State Transfer) is the most common style for web APIs because it builds directly on the way [HTTP works](/computer-science/how-http-works/). This article covers the basics a developer needs to use and design REST APIs well.

## REST API constraints

Roy Fielding defined REST in his 2000 dissertation as a set of constraints:

1. **Client-server:** user interface and data storage are separated, so each can evolve independently.
2. **Stateless:** each request contains all the information the server needs; the server keeps no client session between requests.
3. **Cacheable:** responses say whether they can be cached, reducing load and latency.
4. **Uniform interface:** resources are identified by URIs and manipulated through representations using standard methods, with self-descriptive messages.
5. **Layered system:** clients cannot tell whether they talk to the origin server or to proxies, gateways or load balancers in between.
6. **Code on demand (optional):** servers may send executable code such as scripts.

## Resources and URLs

Design URLs around **nouns** (resources), not verbs, and use plural collection names:

| Action | Method and URL |
| --- | --- |
| List orders | GET /orders |
| Get one order | GET /orders/1001 |
| Create an order | POST /orders |
| Replace an order | PUT /orders/1001 |
| Update some fields | PATCH /orders/1001 |
| Delete an order | DELETE /orders/1001 |
| List items of an order | GET /orders/1001/items |

Use query parameters for filtering, sorting and paging: GET /orders?status=shipped&sort=-date&page=2.

## Representations: JSON

Most REST APIs exchange **JSON**. A request to create an order might send:

```json
{
  "customerId": 57,
  "items": [{ "sku": "PT-100", "qty": 2 }],
  "shipTo": "Pune"
}
```

and the server replies with 201 Created, a Location header pointing to /orders/1001 and the created order in the body. Use consistent naming (camelCase or snake_case, not both), ISO 8601 dates and explicit units.

## Status codes to use

| Situation | Status code |
| --- | --- |
| Successful read or update with a body | 200 OK |
| Resource created | 201 Created (plus Location header) |
| Success with no body, such as a delete | 204 No Content |
| Malformed request or invalid fields | 400 Bad Request |
| Missing or invalid authentication | 401 Unauthorized |
| Authenticated but not allowed | 403 Forbidden |
| Resource does not exist | 404 Not Found |
| Conflict, such as a duplicate | 409 Conflict |
| Validation failed on a well formed request | 422 Unprocessable Content |
| Rate limit exceeded | 429 Too Many Requests |
| Unexpected server failure | 500 Internal Server Error |

Return a consistent error body, for example a code, a human readable message and the field that failed, so clients can handle errors predictably.

## Design best practices

- **Versioning:** include a version in the path (/v1/orders) or a header, and avoid breaking changes within a version.
- **Pagination:** never return unbounded lists; use page and size or cursor based paging, and return links or a next cursor.
- **Filtering and field selection:** let clients ask only for what they need.
- **Security:** always use HTTPS; authenticate with tokens such as OAuth 2.0 bearer tokens; validate every input; apply rate limits; never trust client side checks alone.
- **Documentation:** describe endpoints with the OpenAPI specification so clients and tests can be generated.
- **Statelessness:** keep session state out of server memory so any instance can serve any request and the API scales horizontally behind a load balancer.
- **Caching:** use Cache-Control and ETag headers on read endpoints.

## Testing and documenting a REST API

During development, tools such as curl, Postman or the browser's developer console send requests and show the raw status, headers and body. An OpenAPI description lets teams generate interactive documentation, client libraries and contract tests from one source. Automated tests should check each endpoint for the success case, validation errors, missing authentication, missing resources and permission failures, comparing both the status code and the shape of the JSON. Monitoring in production then tracks error rates and response times per endpoint, so problems are found before users report them.

Rate limits, quotas and clear deprecation notices in responses help clients adapt when an API changes or is under heavy load. Publish a changelog so integrators know what changed and when.

## REST and the backend

Behind the API, a backend application validates requests, applies business rules and reads or writes a database whose tables should be well designed; see [database normalization](/computer-science/database-normalization/). Clean code structure, such as the [SOLID principles](/computer-science/solid-principles/), keeps controllers, services and data access layers separate and testable. Every endpoint should be covered by [integration tests](/computer-science/types-of-software-testing/) that check status codes and response bodies.

Alternatives to REST include **GraphQL**, where clients specify exactly the fields they need in one query, and **gRPC**, which uses binary messages over HTTP/2 for fast service to service calls. REST remains the most common choice for public web APIs because it is simple, cache friendly and works with every HTTP tool.

## REST API interview and viva questions

1. **What does stateless mean in a REST API?** Each request carries all the information the server needs, and the server keeps no client session between requests. This makes scaling and caching simpler.
2. **Which HTTP methods are idempotent?** GET, PUT and DELETE are idempotent, so repeating them leaves the same final state. POST is not, so a retry could create a duplicate resource.
3. **What is the difference between 401 and 403?** 401 Unauthorized means authentication is missing or invalid. 403 Forbidden means the client is authenticated but not allowed to perform the action.
4. **Which status code should a successful create return?** 201 Created, together with a Location header pointing to the new resource.
5. **Who defined REST and how?** Roy Fielding defined REST in his 2000 dissertation as a set of constraints: client-server, stateless, cacheable, uniform interface, layered system and optional code on demand.
