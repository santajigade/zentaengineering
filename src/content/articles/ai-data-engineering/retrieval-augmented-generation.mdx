<Key title="Short answer">

**Retrieval augmented generation (RAG)** is a method that answers a question by first searching a document collection for relevant passages and then giving those passages to a large language model together with the question. The model writes its answer from the retrieved text, so answers can use private or recent documents and cite their sources.

</Key>

Retrieval augmented generation lets a language model answer from your own documents instead of only from what it memorised during training. A plain LLM stores its knowledge in its weights, which are fixed at training time and cannot point to where a fact came from. RAG adds a search step in front of the model: find the passages that match the question, paste them into the prompt, and let the model write the answer from them.

## Why retrieval augmented generation is needed

A [large language model](/ai-data-engineering/how-large-language-models-work/) predicts the most plausible next token. When its training data is thin or out of date on a topic, a plausible answer can still be wrong, and the model has no way to show where the claim came from. It also knows nothing about documents it never saw, such as a plant's own maintenance procedures.

Lewis and colleagues (2020) described this as combining two kinds of memory. The **parametric memory** is the knowledge stored in the generator's weights. The **non-parametric memory** is an external index of text passages that a retriever can search. In their system the retriever was Dense Passage Retrieval (DPR) and the generator was a pre-trained sequence to sequence model, BART. Because the index sits outside the model, it can be replaced to update the system's knowledge without retraining the generator.

## The RAG pipeline

Indexing runs offline, once for the document collection and again when documents change. The query path runs every time someone asks a question.

### Offline indexing

1. Collect the documents: manuals, standards, procedures, reports or web pages.
2. Split each document into short passages, called chunks. Lewis and colleagues split Wikipedia into passages of 100 words, following DPR. Chunks must be small enough to fit several into a prompt but large enough to carry a complete idea.
3. Pass each chunk through an embedding model to get a dense vector. See [tokenization and embeddings](/ai-data-engineering/tokenization-and-embeddings/) for how text becomes vectors.
4. Save each vector with its chunk text and source in a vector index. Moving and cleaning the documents into this store is ordinary data engineering, much like an [ETL or ELT pipeline](/ai-data-engineering/etl-vs-elt/).

### Online query

1. Embed the question with the same embedding model, so the query and the chunks live in the same vector space.
2. Search the index for the k chunk vectors with the highest similarity to the query vector.
3. Put the retrieved chunks and the question into one prompt, with an instruction to answer from the given text.
4. The LLM writes the answer, ideally citing the chunks it used.

## How retrieval works

The retriever scores every chunk against the query. In the vector space model described by Manning, Raghavan and Schütze, a common score is **cosine similarity**, the cosine of the angle between two vectors:

$$
\cos\theta = \frac{\mathbf{q}\cdot\mathbf{d}}{\lVert\mathbf{q}\rVert\,\lVert\mathbf{d}\rVert}
$$

A score near 1 means the vectors point the same way, which for a good embedding model means similar meaning. DPR uses two separate BERT encoders, one for questions and one for passages, and scores a pair by the dot product of their vectors:

$$
\text{sim}(q, p) = E_Q(q)^\top E_P(p)
$$

Karpukhin and colleagues reported that DPR beat the keyword method BM25 by 9% to 19% absolute in top-20 passage retrieval accuracy on open domain question answering datasets. Dense vectors can match a passage to a question that shares its meaning but few of its words.

Comparing the query with millions of vectors one by one is slow. Libraries such as FAISS, described by Johnson, Douze and Jégou, use approximate nearest neighbour search: they return close matches quickly instead of guaranteeing the exact best ones.

## How the generator uses the passages

In the original RAG paper, the generator does not trust a single passage. It treats the retrieved document z as a hidden variable and combines the answers it would give from each of the top-k documents, weighted by the retriever's probability:

$$
p(y \mid x) \approx \sum_{z \in \text{top-}k} p_\eta(z \mid x)\, p_\theta(y \mid x, z)
$$

The paper gives two versions. **RAG-Sequence** uses the same document for the whole answer and then combines across documents. **RAG-Token** can draw on a different document for each generated token. The retriever and generator were trained together, end to end, on question and answer pairs. On open domain question answering, RAG set new state of the art results on several benchmarks, and human raters judged its generated text more factual and specific than a generator without retrieval.

Most RAG systems built today on general purpose LLMs skip the joint training and simply paste the top-k chunks into the prompt.

## Design choices that decide RAG quality

- Chunk size and overlap. Short chunks match the query precisely but may lose context. Long chunks carry context but use up the prompt budget, as the example shows.
- The embedding model. Use one trained for retrieval, and embed queries and chunks with the same model.
- k, the number of chunks. More chunks raise the chance that the answer is included, but they add noise and tokens.
- Keyword plus dense search. A keyword score such as BM25 still helps with part numbers, codes and rare terms that dense vectors can blur.
- Metadata. Store the document title, section and date with each chunk so answers can cite sources and old revisions can be filtered out.
- Evaluation. Measure retrieval with precision and recall, as defined in information retrieval, and check answers against the source chunks.

## Limitations of retrieval augmented generation

- If the right chunk is not retrieved, the model cannot use it and may fall back on its own memory.
- Retrieved text can conflict, be out of date or be wrong, and the model may repeat it.
- Every chunk added to the prompt costs tokens, time and money.
- Wrong or outdated documents give wrong answers, so the collection needs owners and version control like any other engineering record.
- None of this changes the [neural network](/ai-data-engineering/how-neural-networks-work/) inside the LLM. RAG only controls which text reaches its prompt.

## Key formulas for retrieval augmented generation

| Quantity | Formula | Symbols and units |
| --- | --- | --- |
| Cosine similarity | cos θ = (q · d) ÷ (‖q‖ ‖d‖) | q = query vector, d = chunk vector; result from −1 to 1, dimensionless |
| DPR similarity | sim(q, p) = E_Q(q)ᵀ E_P(p) | E_Q, E_P = question and passage encoders; dot product of their output vectors |
| RAG-Sequence output | p(y ∣ x) ≈ Σ p_η(z ∣ x) p_θ(y ∣ x, z) | x = input, y = output, z = retrieved document, sum over top-k documents; η = retriever, θ = generator parameters |
| Chunk budget | n = floor((C − P − R) ÷ L) | C = context window, P = prompt and question, R = reserved answer tokens, L = tokens per chunk |

## Retrieval augmented generation interview and viva questions

1. **What are parametric and non-parametric memory in RAG?** Parametric memory is the knowledge stored in the generator's weights. Non-parametric memory is the external index of passages that the retriever searches at question time.
2. **Why must the query and the chunks use the same embedding model?** Similarity scores are only meaningful when both vectors come from the same vector space, so a query embedded with a different model would not match the stored chunks correctly.
3. **What is the difference between RAG-Sequence and RAG-Token?** RAG-Sequence uses the same retrieved document for the whole output and combines over documents, while RAG-Token can use a different document for each generated token.
4. **How does dense retrieval differ from BM25?** BM25 scores exact keyword matches, while dense retrieval such as DPR compares learned vectors and can match passages that share meaning but not words. DPR beat BM25 by 9% to 19% absolute in top-20 retrieval accuracy in its paper.
5. **How can a RAG system's knowledge be updated?** Add, change or remove documents, re-embed the affected chunks and update the index. The generator does not need retraining.
